# Explain through interactions

Explain unfamiliar mechanisms through concrete examples and visible changes.
Each topic supplies its own domain, interactions and visual language.

## Build a mental model one step at a time

Start with the question the audience needs answered. Show the obstacle before
introducing its mechanism. Use a recognizable object or action: one request,
one changed record, one search, one timeout. Reuse its identity and values across
related slides instead of introducing new opaque examples every time.

Progressive reveals are beats in a spoken explanation. Decide what the audience
should notice on each beat. Sometimes an entire scene appears; sometimes only a
value, a connection, a rejected update or a failure indicator changes. An entry
state may show only the title when setup is needed. Don't animate every element
merely because it can be animated.

Expose interactions, not just component inventories. Show who acts, what is sent,
what changes, and what remains true. Use visible step tabs for a multi-state story.
Keep stable actors in place, use labels with semantic colors, and highlight actual
changes. Distinguish process flows from panels showing the current state.

For failure stories, show the ordinary action first, then the failure, then its
consequence and recovery. A guarantee must have a visible mechanism or a defensible
explanation. A diagram should not imply the guarantee comes from an arrow.

## Compose the wider story

Introduce pieces before assembling the full system when that helps the audience.
A system overview can then walk through one path at a time. If the audience needs
an overview first, give it briefly and return to the components.

A product demo and a technical explanation may reuse the same scene but must
answer different questions. Don't duplicate the interaction without adding a
useful technical layer. A demo can start with one focal element and reveal the
rest when it becomes relevant; this is not specific to chat or maps.

Explain technology choices through their workload, responsibility and meaningful
alternative. Avoid catalog slides naming every vendor. Prefer the few mechanisms
the presenter can defend and extend under questions.

Use short concrete titles: questions for setup, assertions for a takeaway where
appropriate. Delete text that says what the audience already sees. Preserve the
constraint or rationale that changes the interpretation. Avoid marketing language
in technical explanation. Keep evidence and estimates distinguishable without
adding a disclaimer box to every slide.

Review the ending for accumulated repetition. Infrastructure inventories, small
provider details and generic conclusions often duplicate stronger earlier flows.
End with a useful conclusion or discussion topics appropriate to the occasion.

## Collaborate and refine

For interview-led work, offer meaningful alternatives, explain unfamiliar concepts,
record the user's decision, and make it concrete. Research uncertainties that could
change that decision. Don't present proposals as already accepted choices.

For visual feedback, identify the particular confusion and make a bounded revision.
Preserve useful compositions when the problem is wording or pacing. If changes are
hard to see, increase contrast and simplify the scene before adding more narration.

Automated checks establish the artifact's mechanics. Human review establishes
whether the explanation works. A scripted demonstration is not a production
capacity test. Stop when the presentation serves its purpose.
